## Rationale

- **AIR-056.**
  - Clause (e) encodes OD-161's "a mid-session decoder error is logged only, with no notice" (`docs/spec/DECISIONS.md:169`; AMB-108 at `docs/spec/AMBIGUITY_REGISTER.md:118`).
  - Clause (c) stays a start failure, so a decoder that can't be created still gets the notice.
- **AIR-061.**
  - OD-161 replaces rev2's "no notice while covered", which dropped the notice, with S2's hold-and-show-on-uncover.
  - The S2 mechanism is cited, not copied (AIR-041(c) and (d), `docs/spec/REQUIREMENTS.md:51`).
- **AIR-069.**
  - The text is OD-161's verbatim (`DECISIONS.md:169`).
  - `<cause>` uses the bare logged marker (fail-safe):
    - it exposes no port number or exception text on screen;
    - it can be checked against the log exactly;
    - `port busy` is logged as `port busy <proto> <port>` (AT-48, `REQUIREMENTS.md:145`), so the suffix is dropped.
  - "Like S2's notices" brings in AIR-041(b)'s removal at cover start and OD-122's no-re-show. It also brings in once per app start and drop-at-exit (OD-58, OD-101, OD-111 and OD-116, as cited in AIR-041, `REQUIREMENTS.md:51`).
  - AIR-069 previously had no retry, so a failed add is logged only, consistent with AIR-061(b).
  - (d) stays without a notice, because OD-161 names only the three causes.
- **AIR-076.**
  - OD-162 (`DECISIONS.md:170`) fixes the note location, which was a proposal at `REQUIREMENTS.md:86`. It also makes the deadline evaluator-only and makes `carplay present` INCONCLUSIVE.
  - `carplay listener unknown` and a missing record cannot show that CarPlay was disconnected (AIR-079(a), AIR-077(b)). Treating them as INCONCLUSIVE prevents a false GO, which makes this a fail-safe parsing edge under OD-86. Open question 2 lets the owner reverse it.
  - Overriding NO-GO mirrors (g)'s existing `port busy` rule.
- **AIR-078.**
  - OD-160 (`DECISIONS.md:168`) replaces the rev2 (b)/(d) `pm install` route, because of the signer gate (`AMBIGUITY_REGISTER.md:122`; hmg_nemesis `AGENTS.md` §3).
  - The zip shape and limits come from `AGENTS.md` §4.2 and §4.3.
  - Failure detection:
    - NEMESIS parses `pm` text itself (§4.3), but whether it exits non-zero on every `pm` failure is unconfirmed.
    - So (d) also checks the output text and the post-install state in `pkg-list` and `pm list packages`. This also covers a run with Android down, where NEMESIS leaves the APK uninstalled in the tree (§4.3).
    - These checks are fail-safe under OD-86.
  - The directory step stays (e), now gated on (d) passing (OD-159, `DECISIONS.md:167`).
  - Removal is OD-160's route. `nemesis uninstall` removes the APK through `[app.0]`'s `package` (§4.5). The log directory is outside `/data/nemesis/apps/`, so it remains.
  - The `am start` `Error` check is a fail-safe parsing edge.
- **AIR-082.** Only the cited route changes. AT-82 still holds, because it cites AIR-078(b).

## Reversibility and safety

- **AIR-078.**
  - On the unit, the install writes the following:
    - `/data/nemesis/apps/airplay.receiver/` (`NEMESIS.data` plus the APK);
    - a `packages.db` line;
    - the installed APK and its app data;
    - `/data/nemesis/logs/airplay-receiver/`.
  - Staging happens in `/data/local/tmp/nemesis/stage/airplay.receiver/`, which is cleared on reboot.
  - NEMESIS briefly sets `sys.boot_completed=0` to pass the signer gate, and then restores it. That is NEMESIS's own behaviour, not the script's.
  - `nemesis uninstall airplay.receiver` undoes everything except the log directory. The owner can remove the log directory by hand (`nemesis root -c "rm -r /data/nemesis/logs/airplay-receiver"`).
  - A failed install can leave a partial package (a tree or `packages.db` line without the APK). The script does not try to clean it up. `nemesis uninstall airplay.receiver` removes it.
  - No services, hooks or `/system` changes are involved, and nothing is published.
- **AIR-069, AIR-061 and AIR-056.** These change on-screen behaviour only. There is no persistent change, and closing the receiver clears any notice.
- **AIR-076.** This runs on the PC only and reads files from the stick. It writes nothing to the unit.

## Open questions

1. **AIR-078(c), scope:** what should the test zip's `os` and `models` values be? `any`/`any` (installs on every unit) or the owner's unit only (refused elsewhere)? OD-160 requires that they are declared, but does not give the values.
2. **AIR-076(g), scope:** should a run that logs `carplay listener unknown`, or has no `carplay listener` record, be INCONCLUSIVE as drafted, or count like `absent`? OD-162 rules only on `present`.
3. **AIR-069(c), what the owner sees:** is the bare marker (`ParkCast can't start: port busy. Exit and try again.`) the wording wanted for `<cause>`, or should a plainer phrase replace each marker?

## Not verified

- Whether the unit runs NEMESIS 1.16.x, which enforces the metadata limits. The limits are taken from `AGENTS.md` §4.2, not from upstream source.
- Whether `nemesis uninstall` removes the APK by `[app.0]`'s `package` key alone, and whether it removes the app's data directory.
- The exact `am start` error text on KitKat, and how the script finds the app's uid. Both are unchanged from rev2.
- AMB-95 to AMB-98, the receiver-env-probe items, remain open. Nothing here depends on them.
- Current AT-77 and AT-79 are left unchanged. Their text was read, but not reverified against the rev2 review.
