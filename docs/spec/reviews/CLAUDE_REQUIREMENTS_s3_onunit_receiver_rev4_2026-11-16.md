## Requirements

| AIR-049 | (a) The receiver MUST NOT bind, connect to or send to TCP 7000 on the unit, whether CarPlay is on or off. (b) It MUST NOT explicitly bind any local port except AIR-048's six, which rules out DiPO's TCP 5001 and 6030 and UDP 5020, 6000, 6011 and 6020. Kernel-assigned ephemeral ports for outgoing sockets are allowed. (c) It MUST NOT stop, signal or reconfigure DiPO, `mdnsd`, `hostapd`, `dnsmasq` or `wpa_supplicant`. The only way it MAY affect whether `mdnsd` runs is the on-demand start that Android's own `NsdService` makes through netd for an `NsdManager` client, as in AIR-050(a). It MUST NOT open netd's `/dev/socket/mdns`, run `ndc`, set `ctl.start` or `ctl.stop`, use `su` or `nemesis root`, or start or stop any daemon itself. It MUST use `mdnsd`'s own socket only for AIR-050's `dns_sd` registrations. | OD-76, OD-158. (c) OD-164 (was AMB-95). |
| AIR-050 | (a) Only after AIR-048(b)'s port check passes, the receiver MUST wake `mdnsd` through the public `NsdManager` only. It MUST get the manager with `getSystemService(Context.NSD_SERVICE)`, then call `discoverServices("_airplay._tcp", NsdManager.PROTOCOL_DNS_SD, listener)`. It MUST NOT call `registerService` or `resolveService`, so nothing is ever advertised through `NsdManager`, under `ParkCast` or any other name. It MUST ignore discovery results and MUST NOT log them. It MUST NOT use root, set system properties or change any system setting to wake `mdnsd`. (b) The receiver MUST treat `mdnsd` as up only when both of these hold: `onDiscoveryStarted` arrived within 5,000 ms of the `discoverServices` call; and after that, a `dns_sd` client connection to `mdnsd`'s socket `/dev/socket/mdnsd` succeeded, tried every 250 ms for at most 5,000 ms. It MUST then log `mdnsd up`. (c) Next, it MUST register two services with the `dns_sd` client protocol over that socket, each with its full TXT record and with automatic renaming turned off: `_airplay._tcp` with instance name exactly `ParkCast`, and `_raop._tcp` with UxPlay's `<device id>@ParkCast`. It MUST NOT register a service before that service's TXT record is complete. It MUST NOT run UxPlay's built-in mDNS responder or any second responder. When both registrations succeed, it MUST log `advertise ok`. (d) Each of these MUST count as `advertise failed`: the manager is null, or calling it throws `SecurityException`; `onStartDiscoveryFailed` is called; `onDiscoveryStarted` does not arrive within 5,000 ms; when the 5,000 ms connect window ends, the socket is missing (`ENOENT`), permission-denied (`EACCES` or `EPERM`), refusing connections, or otherwise unreachable; a TXT record can't be built; a registration returns an error; a name conflicts. On any of them, the receiver MUST log `advertise failed` with the reason and the error code, withdraw any registration already made, and stop discovery. It MUST NOT accept connections, MUST NOT retry or fall back to another responder, and MUST take AIR-069(c)'s start-failure path. (e) If the `mdnsd` connection closes after `advertise ok`, the receiver MUST log `advertise lost`. It MUST NOT re-register, fall back or show a notice. (f) On stop, the receiver MUST withdraw both registrations and then release its `NsdManager` use with `stopServiceDiscovery`, as AIR-070 orders. (g) The first on-unit run checks whether an app holding only `INTERNET` can open `/dev/socket/mdnsd`. | OD-76, OD-148, OD-150, OD-164 (was AMB-95). Fail-safe under OD-86: (b)'s time limits, (c)'s complete-TXT rule and no automatic renaming, (d)'s failure list with no retry, (e), and not logging discovery results. (e) giving no notice follows OD-161's mid-session rule. |

## Rationale

- **AIR-049, AIR-050 and AIR-070** encode OD-164 (`docs/spec/DECISIONS.md:172`).
  - The evidence:
    - `mdnsd` is not running with CarPlay off, and the only socket is netd's `root system 0660` one (`docs/evidence/RECEIVER_ENV_FINDINGS.md:11-12`).
    - `libmdnssd.so` is present (`:13`).
    - The 4.4 `NsdManager` has no TXT support (`:20-21`).
  - Why `discoverServices` is the waking call:
    - A browse sends queries and advertises nothing, so no TXT-less or spurious service can appear under any name.
    - `registerService` would advertise a service without TXT.
  - How the receiver knows `mdnsd` is up: `onDiscoveryStarted`, then a successful socket connect.
  - Releasing the `NsdManager` use is `stopServiceDiscovery`, placed after deregistration in AIR-070.
  - Which `dns_sd` client implementation the receiver uses is left open, because the rows constrain only the protocol and socket.
  - AIR-068 is unchanged. Connecting to a socket is not a write, and on 4.4 `NsdManager` needs only `INTERNET`.
- **AIR-078** encodes OD-165 (`DECISIONS.md:173`). The value is the owner's `ro.build.product` (`docs/evidence/GEAR_PROBE_FINDINGS.md:84`, AT-64 at `docs/spec/REQUIREMENTS.md:161`). Both keys carry the build because the decision says "its build" for both. The offline check is byte-exact and applies the 1.16 limits (hmg_nemesis `AGENTS.md` §4.2).
- **AIR-076** encodes OD-166 (`DECISIONS.md:174`). AIR-079 is unchanged: it still logs `carplay listener unknown`, and only the verdict's treatment of that line changes.
- **Fail-safe choices under OD-86:**
  - the 5,000 ms and 250 ms limits;
  - no retry after `advertise failed`;
  - the complete-TXT rule;
  - all-or-nothing registration of the two services;
  - `advertise lost` with no notice;
  - discovery results not logged;
  - `present` winning over `unknown` in the same run;
  - the byte-exact `os` and `models` check.

## Reversibility and safety

- **AIR-050.** Getting the manager and starting discovery make Android's `NsdService` start `mdnsd` through netd. No file, property or setting changes. `stopServiceDiscovery` and the process exit release the use, and `NsdService` then decides whether `mdnsd` keeps running (Open question 2). Browse queries go only to the hotspot (`wlan0`). The registrations are withdrawn at stop. If the process dies, they lapse when `mdnsd` drops the client connection.
- **AIR-049.** It adds no new action on the unit. It narrows what the receiver may touch.
- **AIR-078.** The `os` and `models` values are metadata in the test zip. `nemesis uninstall airplay.receiver` removes the package as before.
- **AIR-076.** It changes the PC evaluator only. Nothing changes on the unit.

## Open questions

1. **Scope, and what the owner sees: the `models` value.** hmg_nemesis `docs/community-reference.md:18` says `models` is matched against the unit's model folder, such as `cvev_us`, not against a build string. If so, `models=CVEV.CAN.0000.V015.011.260206` may not match the owner's own unit. The owner could then get NEMESIS's accept-risk prompt, or a refusal, on their own unit. Should `models` instead name the CA unit's model folder, which a read-only probe would first have to find, with `os` keeping the build string?
2. **Safety, and what the owner sees: `mdnsd` after ParkCast exits.** On 4.4, `NsdService` may stop `mdnsd` once its last `NsdManager` client disconnects, which happens when ParkCast exits. If DiPO relies on an `mdnsd` it did not start through `NsdManager`, wireless CarPlay discovery could be affected until DiPO restarts it. Is that acceptable for S3, given runs are done with CarPlay disconnected (AIR-079(a))? Or should the first on-unit run also check that wireless CarPlay reconnects after the receiver exits?

## Not verified

- **General Android 4.4 knowledge, not repository evidence:**
  - `getSystemService(NSD_SERVICE)` connects an AsyncChannel to `NsdService`, which starts `mdnsd` through netd (`mdnssd start-service`) for its first client and may stop it when the last client disconnects.
  - `discoverServices` reports `onDiscoveryStarted` only when `mdnsd` answers.
  - `stopServiceDiscovery` does not end the client connection.
  - `NsdService` enforces `INTERNET` and is on by default (`NSD_ON`).
  - `mdnsd`'s client socket is `/dev/socket/mdnsd`, and stock 4.4 creates it as `0660 mdnsr inet`.
  - `dns_sd` `DNSServiceRegister` takes TXT records and `kDNSServiceFlagsNoAutoRename`.
- **Not checked here:**
  - The socket's real path and mode on this unit while `mdnsd` runs (`RECEIVER_ENV_FINDINGS.md:18`). AT-50 `@unit` checks it.
  - Whether `mdnsd` creates the socket within 5,000 ms of discovery starting.
  - Whether an app can load the unit's `libmdnssd.so`, or needs a bundled client.
- **UxPlay behaviour:** the `_raop._tcp` instance form `<device id>@ParkCast` and the TXT contents come from UxPlay's normal behaviour, not from this repository.
- **NEMESIS `os` and `models` matching:**
  - How NEMESIS 1.16 matches `os` and `models`, beyond `any` matching every unit.
  - Whether `nemesis install` run from a stick script applies the Manager's compatibility or accept-risk check at all.
  - These sources are in hmg_nemesis (`docs/community-reference.md:18`, `docs/creating-a-package.md:108`, `AGENTS.md` §4.2), outside this stage root.
