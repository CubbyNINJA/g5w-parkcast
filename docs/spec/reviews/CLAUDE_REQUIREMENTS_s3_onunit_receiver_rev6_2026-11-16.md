## Rationale

- **AIR-048 / AT-48.** OD-175 (`docs/spec/DECISIONS.md:183`) makes `hotspot address missing` a fourth start-failure cause with the shared notice. So (d) now points to AIR-069(c) instead of (d), and AT-48 expects exactly one notice instead of none. The rest of (d) is unchanged and stays under OD-174 (`DECISIONS.md:182`): it binds nothing, never falls back and never retries.
- **AIR-069 / AT-69.** (c) now lists five causes, and its text and bare marker follow OD-161 and OD-167 (`DECISIONS.md:169,175`). (d) is now limited to failures outside those five. Two edge cases are resolved fail-safe under OD-86 (`DECISIONS.md:94`): (d) says outright that those other failures show no notice, and `<cause>` explicitly excludes library error, interface, address and key path or name, so the notice can't leak what AIR-083(d) keeps out of the logs. The existing (f) already covers a run with both new causes in one app start: one notice, and the first cause logged wins. AT-69 now names this case.
- **AIR-083 / AT-83.** OD-176 (`DECISIONS.md:184`) means the receiver stops with the notice, leaves the key file alone, and uninstalling resets the key. (c) now points to AIR-069(c), and (f) is the existing reset path. Under OD-86, "MUST NOT make a replacement key for an existing file" is scoped so it doesn't contradict the failing-write case, where no file exists yet. AT-83 expects exactly one notice instead of none.

## Reversibility and safety

Nothing new is installed or changed on the PC or the unit. The only on-screen change is the existing `TYPE_TOAST` start-failure notice, shown for two more causes. It is held while covered, and at most one appears per app start. The key file is still never touched on failure. It is removed only by `nemesis uninstall airplay.receiver`, under AIR-083(f) and AIR-078(g), as before.
