## Rationale

- **AIR-042, 043, 046, 049, 053, 055, 064, 065, 067, 070, 071**: only the third column changes. Under OD-158 (`docs/spec/DECISIONS.md:166`), the former "proposal" clauses are accepted as drafted, and AIR-071's markers are left to the scenarios (`REQUIREMENTS.md:52-92`).
- **AIR-044**: OD-157 (`DECISIONS.md:165`) fixes the dependency lines. A pin outside them failing the build is the fail-safe build check.
- **AIR-048, 050, 056, 069**: OD-150 (`DECISIONS.md:158`) names three start failures. Each now routes to one start-failure path, AIR-069(c), so the notice and staying-open rule is stated once. Two parts are my reading of "existing toast-window style": the form, and AIR-040(e)'s time on screen (`REQUIREMENTS.md:50`). A crash still ends the process: OD-150 covers start failures, not crashes. AIR-050(b) is OD-148 (`DECISIONS.md:156`). Turning off automatic renaming in AIR-050(e) is fail-safe: it stops the unit advertising under a name other than `ParkCast`.
- **AIR-054**: OD-153 (`DECISIONS.md:161`). This matches AIR-010(c), where a sound note never changes a verdict (`REQUIREMENTS.md:20`).
- **AIR-057**: the black screen while blocked comes from OD-150.
- **AIR-062, 063, 078(e)**: OD-156 (`DECISIONS.md:164`). The app's uid exists only after `pm install`, so the directory step must come between install and start. That ordering is a timing edge, resolved fail-safe: the script does not start the receiver without a usable log directory. I read `airplay.receiver` as the NEMESIS id used in the path, and not as the Android application id.
- **AIR-068**: OD-152 (`DECISIONS.md:160`). The check runs on the built APK, because merged library manifests can add permissions.
- **AIR-073**: OD-155 (`DECISIONS.md:163`), the model-only rule.
- **AIR-074, 078**: OD-149 (`DECISIONS.md:157`). KitKat `pm` exits 0 even on failure, so its output text decides the result (fail-safe parsing).
- **AIR-076**: OD-154 and OD-155 (`DECISIONS.md:162-163`). The note parsing, the run-wide note being ambiguous across several rendered sessions, run-wide INCONCLUSIVE on port or advertise failure, and the exclusive deadline at 600 s are all fail-safe: none of them can produce a GO the evidence does not support. The 10-minute window follows AIR-007(b) and AIR-011(c) (`REQUIREMENTS.md:17, 21`).
- **AIR-079**: OD-151 (`DECISIONS.md:159`). The owner chose to log only, overriding the draft's "refuse". `unknown` in (d) is a fail-safe parsing edge that keeps OD-151's behaviour.
- **AIR-082**: the route is now decided (OD-149).

## Reversibility and safety

- **AIR-078 install script** (on the unit, as root): it installs the APK, creates `/data/nemesis/logs/airplay-receiver/` (app uid, 0700) and starts the activity.
  - Undo: `pm uninstall` removes the app. The log directory remains by design (AIR-078(c)) and can be removed by hand as root.
  - The script does not touch `/system`, properties or the network. The signer gate is left to NEMESIS.
  - On failure, the receiver is not started. An APK that installed but failed the directory step stays installed until it is uninstalled.
- **AIR-074 copy script** (as root): read-only on the unit. It writes only to the stick. A partial copy is marked incomplete.
- **AIR-044, 046** (PC): build outputs and dependency sources only. Delete the build directories to undo.
- **Gate safety**: unchanged. Every start-failure path keeps video blocked (AIR-069(c), (d)). The CarPlay log-only rule (AIR-079(c)) does not bind or connect to TCP 7000 (AIR-049).

## Open questions

1. **Start-failure notice** (what the owner sees):
   - What text should each of `port busy`, `advertise failed` and `decoder unavailable` show?
   - Should a notice suppressed while the receiver is covered (AIR-061(c)) be dropped or shown later? This draft drops it.
   - Should a mid-session `decoder error`, or any other start failure, also show a notice? OD-150 lists only three, so this draft shows none for them.
2. **Owner note file** (what the owner writes): `owner-note.txt` in the run's `NEMESIS-diag/airplay-receiver/<timestamp>/` folder is a proposal. Is that where the owner wants to write it?
3. **10-minute timeout**: this draft enforces it only in the evaluator. Should the receiver itself also stop or change the screen at 10 minutes, which the owner would see?
4. **Scope**: does a run that logs `carplay listener present` still meet AIR-079(a)'s "CarPlay disconnected" and AIR-077(b)'s claim? It may only mean wireless CarPlay is enabled, not connected.

- How the script can find the app's uid with toolbox tools only, and whether KitKat toolbox `chown` accepts it.
- That the unit's `mdnsd` honours turning off automatic renaming (AMB-95 is still open).
- That OpenSSL 3.0 and libplist 2.x build for NDK r25c at API 19.
