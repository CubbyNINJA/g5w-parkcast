## Rationale

**AIR-019.** Check-on behaviour of (h) and (i) is kept as the prompt asks. The only check-on changes are OD-104's literal tokens (`docs/spec/DECISIONS.md:112`). (h) now sends check-off logging to AIR-021(b), as OD-103 requires (`DECISIONS.md:111`). "Enabled" is read from the effective flag value, so a fallback start (`REQUIREMENTS.md:34`, every AIR-023 fallback resolves to `true`) keeps the check-on failure record, `ignored` records and notice. That is the fail-safe reading under OD-86 (`DECISIONS.md:94`): when the configuration is in doubt, the gate and its diagnostics behave as if the check is on. OD-104 tokens: (g) gets `during sleep` and `after resume`, and (h) gets `status=<value>`, `status=missing` and `status=non-integer`. Writing `<value>` as a decimal integer is an OD-86 choice that gives the tests one oracle. (f)'s `registerSystemOffResponder` ban is now proven by OD-104's static scan rather than a synthetic service trace (`docs/evidence/SLEEP_SIGNAL_FINDINGS.md:11`, `:38`). The notice wording stays open (AMB-73). Tests only assert that the two notices' texts differ (OD-104). OD-88 (`DECISIONS.md:96`), OD-91 (`:99`) and OD-100 to OD-102 (`:108`–`:110`) are kept as they are.

**AIR-021.** This row encodes OD-103(a) and (b) (`DECISIONS.md:111`, AMB-72 at `docs/spec/AMBIGUITY_REGISTER.md:82`). With the check off, a registration failure blocks nothing (OD-83, `DECISIONS.md:91`), so it is logged as information and no notice is shown. These are the OD-86 choices, made so that tests have an oracle and the log carries no failure wording:
- the fixed text `ACC registration unavailable`;
- the cause names reused from AIR-019(h);
- a ban on `fail` and `error` in any letter case;
- no exception class, message or stack trace;
- no record at all for later broadcasts, rather than a renamed `ignored` record.

A missing-extra sticky state is excluded because AIR-019(h) does not treat it as a registration failure. OD-45 (`DECISIONS.md:53`) is cited for the flag's start-time semantics. AIR-040's logging-failure notice is kept (OD-49, `DECISIONS.md:57`).

**AIR-025.** This row encodes OD-103(c). The prompt asked three things:
- **Relation to the start record:** a separate record, so the existing start record contract (OD-79, `DECISIONS.md` OD-79 row) and its `reason=` oracle stay unchanged.
- **Order:** it is the first record of the app start. The receiver must resolve the flag before it writes any record, so nothing else can come first.
- **Flag:** it uses the effective value. Fallbacks resolve to `true` (`REQUIREMENTS.md:34`), so only an explicit `false` writes it. A wrongly written "check off" line during a fallback would misreport a gate that is actually on, which is why this is the fail-safe direction.

If the write fails, it is an AIR-040(d) logging failure. It is not retried, because a late "first line" would be out of order and could be mistaken for a later start. It does not change the flag or the gate. The later records are still attempted. All of these are OD-86 choices.

**AIR-026.** This row encodes OD-104's third clause: the reason of a gate change names the Park reading that caused it, with its value and receipt time. The time uses AIR-019(b)'s receipt-age clock, so the logged time is the one the gate actually acted on. Transitions with other causes (timeout, age past 2 s, sleep or resume, flag change) name their own cause and never cite a reading. This keeps the log from inventing a Park value where none was returned. Both are OD-86 choices. Field order and time format are left to the implementation, as AIR-025 already does. OD-71 (`DECISIONS.md:79`) and OD-49 (`:57`) are kept.

**AIR-040.** (b) now says the logging-failure notice applies with either flag value. New (d) puts the two OD-103 records under it with no registration-failure notice. OD-103 removes only the failure wording and the registration notice, not OD-49's logging notice (`DECISIONS.md:57`). OD-58 (`:66`) and the OD-101 separate allowances (`:109`) are unchanged.

**AIR-039.** Unchanged. The new records follow it through the existing "MUST follow AIR-039 and AIR-040" references.

**Tiers.** The OD-104 static scan is `@offline` evidence that the receiver's code contains no such call. It does not show what the unit's power service does. All `@offline` results are specification evidence only (`specs/README.md`).

## Reversibility and safety

- These are changes to the spec text only. Nothing is installed or changed on this PC or the unit by this revision.
- Once implemented, the affected behaviour is limited to receiver log records under `/data/nemesis/logs/airplay-receiver/` and on-screen notices.
- **Check off:** the registration-failure notice is removed, and the wording of log records changes (informational record, no `ignored` records, a new `parking check off` first record). The gate already blocks nothing in this mode, so it is not made less safe. The logging-failure notice is kept.
- **Check on, including every fallback:** gate behaviour, notices and record content are unchanged, apart from OD-104's added literal tokens and the Park reading named in gate-change reasons.
- To undo, revert the ten rows to revision 11.
