## Rationale

**AIR-019.** OD-91 (AMB-68) is encoded as the new clause (h). A registration that throws, or one that returns no sticky state, starts the receiver asleep and logs the failure. With the check on, nothing mirrors for the rest of that run, because clause (d) blocks video while asleep and no getter call ever runs. The prompt quotes OD-91 as "until the receiver restarts and registration works" (`docs/spec/DECISIONS.md:99`). That wording is the basis for two choices: registration isn't retried, and a later broadcast in the same run doesn't resume. A retry, or a broadcast taken as a resume, would allow mirroring before a restart. The registration call that returns no sticky state still leaves the broadcast receiver registered, so later broadcasts can reach it. The evidence says this is possible: the broadcast is sent only on a state change, and a start-up `5`→`0` was seen in the broadcast history (`docs/evidence/SLEEP_SIGNAL_FINDINGS.md:11`, `:41`). Clause (h) says those broadcasts are ignored.

The OD-86 fail-safe choices made here:
- The receiver counts as asleep until registration returns or throws.
- The failure record carries the literal `ACC registration failed` and the cause, `exception` or `no sticky state`.
- An ignored broadcast is logged with the word `ignored` and its status. That is diagnostic only and changes no state.
- A sticky intent with a missing or non-integer extra stays under OD-88 (asleep, and a later awake value resumes). It is not a registration failure, because registration did return a state.
- After a throw, exit doesn't try to unregister, so a second exception can't block exit.

Clause (f) gains only the pointers to (h). The "(f) and (g)" choices are now cited as OD-88, which recorded them after revision 9 (`docs/spec/DECISIONS.md:96`).

**AIR-021.** OD-91 asks that the check-off case stay consistent with AIR-021(b) and OD-83 (`docs/spec/DECISIONS.md:91`): polling stops while the unit counts as asleep, and the gate blocks nothing. A failed registration therefore means no Park polling for the rest of that run, no parking-gate block, and the same logging as with the check on. The time before registration returns is treated the same way.

## Reversibility and safety

No files were edited and nothing was installed.

- AIR-019(h) and AIR-021(b) change only runtime state handling and log lines. Nothing is written on the PC or the unit except log records under `/data/nemesis/logs/airplay-receiver/` (AIR-039 limits). The receiver doesn't retry registration, so a failure can't cause repeated calls to the system. It never uses a system-off responder.
- Fail-safe outcome with the check on: a failed registration means no mirroring and no Park polling until the receiver restarts. Undo: restart the receiver once registration works. A head-unit reboot also restarts it.
- With the check off, mirroring is unaffected by a failed registration. Only Park polling stops for that run.
- After a throw, nothing is registered and nothing is left behind. After a registration that returns no sticky state, the broadcast receiver is unregistered at exit, as in revision 9.

## Open questions

1. **What the owner sees after a registration failure with the check on.** OD-91 requires a log record only. The owner would then see no mirroring and nothing on screen to explain it. AIR-040 has an on-screen notice for logging failures, but no requirement shows one for a blocked gate. Should a registration failure also show an on-screen notice, at most once per app start? No change is drafted until the owner decides.
2. **Starting before the first ACC broadcast.** The broadcast is sticky only after `MicomPowerService` first sends it on a state change (`SLEEP_SIGNAL_FINDINGS.md:11`; a start-up `5`→`0` was observed at `:41`). If the receiver starts earlier than that, for example at early boot, registration returns no sticky state. Under OD-91, nothing then mirrors with the check on until a restart. This is OD-91 working as decided. It changes what the owner sees after a cold boot only if the receiver can start that early. Whether the start should be scheduled after the first ACC broadcast is the owner's call (launch scope). Nothing is drafted for it.
