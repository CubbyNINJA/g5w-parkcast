## Rationale

**AIR-017.** Clause (b) pointed only at AIR-019(d) for sleep, and AIR-019 applies only with the check on. OD-83 stops polling at sleep with the check off too, so (b) now also points at AIR-021(b). AT-17 is unchanged.

**AIR-019.** OD-84 makes the resume re-read a call started after resume. A pre-sleep call never counts, even when it replies after resume within 200 ms of invocation. The ban on overlapping calls (AIR-017(e)) still applies, so the re-read waits for a pre-sleep call that is still pending. No signal is named. The rest of the row is the current row verbatim.

**AIR-021.** OD-83: with the check off, polling still stops at sleep and the gate blocks nothing, including after resume. The row is split into clauses so each can be tested on its own. Rev 7 open question 5 is closed.

**AIR-023.** OD-79: a line with whitespace around `=` is an occurrence of the key, so beside a well-formed line it conflicts. OD-80: values are compared exactly and case-sensitively after whole-line trimming. The resulting flag value is `true` in every new case. Rev 7 open questions 1 and 2 are closed.

**AIR-025.** OD-79 names a lone spaced line "the unrecognised value"; beside a well-formed line it is a conflicting duplicate, named as one. OD-81 puts the phrase literally in a `reason=` field. Rev 7 open question 3 is closed.

**AIR-039.** OD-82: rotate before a write that would cross 2,621,440 bytes, so no file exceeds that size and no record is split.

## Reversibility and safety

No files were edited and nothing was installed.

- AIR-017, AIR-019 and AIR-021 change only runtime polling and gate decisions. With either flag value, no getter calls are made during sleep. Getter access stays read-only. With the check on, the stricter re-read rule can only keep video blocked longer.
- AIR-023 and AIR-025 change parsing and log text only; every new parsing outcome falls back to check-on.
- AIR-039 keeps logs within the existing 5,242,880-byte total and adds a 2,621,440-byte limit per file.

## Open questions

1. **Sleep and resume signals:** which head-unit event marks sleep entry and resume? Being identified; not named here.
2. **Spaced lines compared with each other:** two identical `video.require_park = false` lines: one unrecognised value, or a conflicting duplicate key? Do lines that differ only in spacing around `=` conflict? Does `video.require_park =false` (one side) count as "around `=`"? The flag is `true` in every reading; only the logged cause differs.
3. **Start-record format:** does an explicit (non-fallback) read also use the `reason=` field, and with what text? Field order and separators are not fixed.
4. **Oversized record:** a single record larger than 2,621,440 bytes can't meet both "no file exceeds 2,621,440 bytes" and "no record is split or trimmed". Is it dropped, does it break one of the limits, or something else?
5. **Pre-sleep reply after resume:** besides not counting as the re-read or permitting video, does it count as an observation for receipt age or logs? With the check off, is a reply during sleep discarded? Logs only, not permission.
6. **Resume timing:** does the re-read start immediately at resume or on the 200 ms schedule? Should a call still pending from before sleep hold up the re-read indefinitely (drafted, per AIR-017(e)), or be abandoned at resume?
