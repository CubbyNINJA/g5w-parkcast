Further logging failures at `F+1000 ms`, and after the notice is shown or given up, add no attempt and do not move the retry. Logging recovering at `F+2000 ms` does not cancel the retry. Make both attempts fail: no third attempt occurs up to `F+60 s`, and a later logging failure adds none. With `true` and a sticky `0` start, deliver `6` at `F+1000 ms` and `0` at `F+3000 ms`, and separately `0`→`2` at `F+1000 ms`: the retry is still made at exactly `F+5000 ms`. Start exit at `F+3000 ms`, and separately at exactly `F+5000 ms`: no retry is made, exit completes without waiting for it, and the next app start's first logging failure makes a new first attempt. With `true`, combine with an ACC registration failure: fail both first attempts at the same `F` and both retries occur at `F+5000 ms`; fail only one notice's first attempt and the other is shown at its own time, with only the failed one retried; neither notice's attempts move, use up or suppress the other's. A notice that fails to show, with no logging failure, produces no logging-failure notice. Through every case the gate decision, effective flag value, getter schedule, registration calls, and audio and connection traces are unchanged. **`@unit`:** Independently observe the notice count and unchanged gate behavior across repeated faults and restart, and, if a registration failure was reached, that both notices appeared, and for a `false` start with a logging fault, that only the logging-failure notice appeared. Record each notice's form (a short toast) and, if a notice failed to show, whether a retry appeared about 5 s later; list a notice that failed to show as unexercised if the unit gave none. Retain evidence outside the failed receiver log. |

Tiers: every new criterion is `@offline`, run with a synthetic UI double, a controlled clock and synthetic traces, and is specification evidence only. The `@unit` additions ask for independent screen observation of the toast and any retry, and list a show failure as unexercised when the unit gives none. Nothing is claimed at `@pc`. No new check depends on hardware toast timing.

## Rationale

**AIR-019(i), form and text.** OD-106 (`docs/spec/DECISIONS.md:114`) fixes the registration-failure notice as a short toast "in the same form and for the same duration as the logging-failure notice", with the owner's exact text. The text is copied byte for byte, with ASCII apostrophes. The old "identify the reason" and "distinguishable" wording is dropped because an exact text replaces both: the text says mirroring is off because the power state could not be read, and AIR-040(e) still requires the two texts to differ. AMB-73 (`docs/spec/AMBIGUITY_REGISTER.md:83`) asked about wording, timing and duration. OD-106 answers wording and duration but records no timing, so making the first attempt at the clock time registration throws or returns no sticky state takes AMB-73's own proposal ("Shown when the failure is detected"). That is a timing edge case resolved fail-safe under OD-86 (`DECISIONS.md:94`): it is the earliest point the failure is known, it adds no delay that could be mistaken for success, and it gives tests an exact oracle. Open question 3 asks the owner to confirm it, because it is what the owner sees. Every OD-102 edge case in clause (i) (`DECISIONS.md:110`) is kept word for word: the effective flag, the fallback to `true`, shown whether or not the record was written, the excluded cases, and the separate allowance.

**AIR-019, OD-108 note.** OD-108 (`DECISIONS.md:116`) defers the early-start case to the package slice. With launch from NEMESIS Manager (OD-95, `DECISIONS.md:103`) that case cannot happen, and OD-91 (`DECISIONS.md:99`) stands. The note is in the decision column only, so clause (h) is unchanged. AMB-71 (`AMBIGUITY_REGISTER.md:81`) moves to the decided list.

**AIR-021, OD-108 note.** The check-off behaviour of a start with no sticky state is AIR-021(b) (`docs/spec/REQUIREMENTS.md:31`), so the same deferral note goes there and the requirement text is untouched. AT-21 (`REQUIREMENTS.md:76`) needs no change: with the check off no registration-failure notice is shown, and any logging-failure notice there follows AT-40, which now carries the retry cases for both flag values.

**AIR-040(b), (e).** OD-106 says the registration-failure notice matches the logging-failure notice's form and duration, and AIR-040 never stated that form. So the shared form goes in AIR-040, where both notices can point to it, rather than being repeated in each row. "Short toast" is encoded as a text toast with duration `Toast.LENGTH_SHORT` and no custom view. That is the literal Android meaning of OD-106's words and gives an observable oracle (a synthetic UI double records the duration constant). Excluding dialogs, notifications and overlays stops a later draft from widening the form. The logging-failure first attempt at the clock time of the failure is the same fail-safe timing choice under OD-86 as for the registration notice, and matches OD-49's "reported once on screen" (`DECISIONS.md:57`) and OD-58 (`DECISIONS.md:66`). The logging-failure notice's text is not decided. AIR-040(e) requires only that it differs, as OD-104 (`DECISIONS.md:112`) already set for tests, and open question 1 lists it.

**AIR-040(f), what "fails to show" means.** OD-107 (`DECISIONS.md:115`) needs a failure that can be observed. The only failure the receiver can observe is the toast create or show call throwing, for example `Toast.makeText` or `show()` raised off a thread that is not ready for UI work. A test double can produce exactly that. Android gives no result when a queued toast is later dropped or hidden, so a call that returns normally counts as shown and is not retried. Without that rule the retry would rest on something no test could see. This is a timing and parsing edge case resolved fail-safe under OD-86. The silent-drop case is listed under Not verified.

**AIR-040(f), retry timing and allowance.** The retry is exactly 5,000 ms after the failed attempt, on the same clock AIR-019(b) uses for receipt age (the clock AIR-026 at `REQUIREMENTS.md:36` already names). It is not made earlier, so the boundary is exact at `F+4999`/`F+5000` like the 200 ms and 2 s boundaries elsewhere in AT-19. OD-107 says the retry "is still within that notice's once-per-start allowance", so both attempts are in one allowance and a notice given up stays given up. Further failures of the same kind do not start a new attempt or move the retry: moving it would let a stream of faults hold the notice off forever. A given-up logging-failure notice counts as shown for (c) and (d), so the "if that app start has not shown one" wording there cannot reopen the allowance. A logging recovery does not cancel the retry, because the owner should still learn that logging failed in that run (OD-49). Each notice keeps its own allowance (OD-58 with OD-101, as clause (c) already says), so one notice's retry cannot use up, delay or suppress the other's. When both are due at the same instant both are attempted, and the order is not specified, so no test may depend on it. A show failure is not a logging failure. Otherwise a broken UI would fire the logging-failure notice through the same broken UI, which helps nobody and couples the two allowances.

**AIR-040(f), sleep and exit.** OD-107 asks for one retry "5 s later in that run" and makes no exception for sleep. The registration-failure notice is always shown while the receiver counts as asleep (AIR-019(h)), so gating notices on being awake would cancel that notice every time. So ACC changes neither delay nor cancel an attempt. This is the literal reading, not added policy. Whether the screen is visible during ACC `6`, `7` or `255` is not established (`docs/evidence/SLEEP_SIGNAL_FINDINGS.md:18-43`), so open question 2 asks the owner. At exit, a retry that is not yet due is dropped. Exit never waits for it, and it never carries into the next start, which has fresh allowances (OD-58, OD-101). That keeps exit bounded and follows OD-107's "in that run". It is a timing edge case resolved fail-safe under OD-86.

**AIR-040(f), no side effects.** As in OD-102 (`DECISIONS.md:110`) for showing or failing to show, waiting, retrying and giving up change nothing in the gate, the effective flag, polling, registration, audio or the iPhone connection. A notice is only a report. It never takes part in the safety decision.

**AT-19 and AT-40.** Each new requirement clause has an `@offline` criterion with an exact oracle: the registration text verbatim, `Toast.LENGTH_SHORT`, no custom view, first attempt at the failure time, no attempt at `F+4999 ms`, exactly one attempt at `F+5000 ms`, none after a second failure up to `F+60 s`, no retry after a first attempt that succeeds, no move or cancel under ACC changes, logging recovery or repeated faults, exit at `F+3000 ms` and at exactly `F+5000 ms` dropping the retry, both notices failing together, and a show failure not producing a logging-failure notice. AT-19's sentence "Make the UI double fail to show the notice" is replaced by the retry block, which keeps its three assertions (gate blocked, no getter call, no second registration call). OD-104's "no wording is asserted" now applies only to the logging-failure notice, so AT-19 drops that parenthesis and asserts the OD-106 text exactly. AT-40 states that the logging-failure wording is not asserted.

## Reversibility and safety

- These are specification text changes only. Nothing is built, installed or run on the PC or the head unit, and no file in the repository was edited by this draft.
- In the receiver, a toast is transient UI. A notice attempt, its retry and giving up write nothing and change no setting. They persist nothing past the app start (the allowances reset at the next start), and they do not touch stock restrictions (AIR-021(c)).
- Safety direction is unchanged. A notice never permits video, never blocks video by itself, never moves the gate, and never starts polling or retries registration. A failed or dropped notice therefore cannot weaken the parking gate, and a retry cannot delay a block. Video blocking under AIR-019 stays immediate and does not depend on any notice.
- Worst case if the retry rule is wrong: the owner sees a notice twice or misses it once. Mirroring stays blocked in the registration-failure case either way, and the log record (AIR-019(h)) still exists when logging works.
- Reversal is cheap. Removing (f) or changing 5,000 ms touches only AIR-040, the AIR-019(i) pointer and two AT rows.

## Open questions

1. **Logging-failure notice text.** OD-106 fixes only the registration-failure text. AIR-040(e) requires the logging-failure notice to be a short toast whose text differs, and asserts nothing else. What should it say? This is what the owner sees, so it is not mine to decide.
2. **Retry while the head unit is asleep.** Following OD-107 literally, a retry falls due even during ACC `6`, `7` or `255`, when the display may be dimmed or off (not established, see Not verified). The registration-failure notice always happens while the receiver counts as asleep. Should a retry that falls due during sleep still fire, as drafted, or wait for resume? This changes what the owner sees.
3. **When a notice first appears.** OD-106 gives form, duration and text but not timing. The draft shows each notice the moment its failure is detected (AMB-73's proposal), resolved under OD-86 as a timing case. If the owner wanted a notice held until something else happens (for example the first frame from the iPhone, or the next resume), the draft is wrong. Please confirm "when detected".
4. **"Short toast" = `Toast.LENGTH_SHORT`.** I read the owner's "short toast" as Android's short duration constant (about 2 s in stock KitKat, not measured on this unit). If the owner meant a different length, AIR-040(e) and both AT rows change.

## Not verified

- **Toast duration on the unit.** About 2 s for `Toast.LENGTH_SHORT` comes from stock AOSP (`SHORT_DELAY` 2000 ms in KitKat's NotificationManagerService). The Gen5W firmware was not checked, and OEM binaries were not opened (role-file rule).
- **Silent drops.** Whether KitKat on this unit drops toasts without an exception, for example for an app whose notifications are blocked, a full toast queue, or a background app. The draft treats such a drop as shown because the receiver cannot observe it. I have no evidence of how often it happens.
- **UI readiness.** Whether the receiver's toast call can actually throw on this unit at registration time or log-failure time, so whether a retry ever happens in practice. AT-19 and AT-40 `@unit` list it as unexercised if not seen.
- **Display state during sleep.** Whether the screen shows anything during ACC `6` (delay mode), `7` (preparing system off) or `255` (off). `SLEEP_SIGNAL_FINDINGS.md:14-43` records only the `0`→`2`→`0` sequence observed. The long-off sequence was not exercised.
- **Clock behaviour across sleep.** Whether the receipt-age clock keeps advancing through deep sleep on the unit, which decides when a retry pending across sleep really fires. Not checked.
- **Other files.** `specs/features/*.feature` and `docs/spec/TRACEABILITY.md` were not read, as instructed, so I have not checked these rows against the scenarios or the trace table being edited in parallel.
- **Prose re-review.** No critic agent was run on this draft. A read-only, single-output role was assumed to rule that out.
