## Rationale

**AIR-019(i).** This clause encodes OD-101 as the owner worded it (`docs/spec/DECISIONS.md:109`; AMB-70 is decided at `docs/spec/AMBIGUITY_REGISTER.md:80`). With the check on, a registration failure under clause (h) means nothing mirrors for the rest of the run (OD-91, `docs/spec/DECISIONS.md:99`; OD-100, `:108`), and the notice explains why the screen is blank. The two allowances are separate because the decisions require it, not by choice. With a shared allowance, whichever notice came first would suppress the other. A log-create failure at start, before registration returns, would then break OD-101, and a registration failure that came first would break OD-49 and OD-58 (`docs/spec/DECISIONS.md:57`, `:66`). The edge cases below are settled with the fail-safe choice under OD-86 (`docs/spec/DECISIONS.md:94`):
- **Flag value.** It is the effective value for that start, including the fallback to `true` (AIR-023). That way, a missing or broken `receiver.conf` cannot hide the reason video is blocked.
- **Record write.** The notice does not depend on the `ACC registration failed` record being written. Otherwise a logging fault would hide a safety-relevant explanation.
- **When no notice is shown.** None while registration is pending, for a returned sticky state with a missing extra, or for ignored broadcasts. None of these is a registration failure under clause (h), so a notice would be false. It also stops repeated broadcasts from producing repeated notices.
- **Display is UI only.** Showing the notice, or failing to show it, does nothing to the gate, getter, registration, audio or connection. A UI fault therefore cannot unblock video or end the session.

Because registration runs once per start and is never retried (clause (h)), "at most once per app start" follows naturally. The clause only makes it explicit. Evidence for the broadcast and registration behaviour is at `docs/evidence/SLEEP_SIGNAL_FINDINGS.md:11` and `:41`.

**AIR-021.** OD-101 is limited to "with the parking check on" (`docs/spec/DECISIONS.md:109`). With the check off, a registration failure blocks nothing (OD-83, `docs/spec/DECISIONS.md:91`), so there is no blank screen to explain. OD-45 (`docs/spec/DECISIONS.md:53`) says nothing is shown on screen about the flag itself when the check is off, but it does not cover a registration failure. So this row neither requires nor forbids a notice with the check off, and the question goes to the owner (Open question 1) instead of being invented here. AIR-040 applies with either flag value, so its notice still applies.

**AIR-040(c).** Clause (c) states the separate-allowance rule from AIR-040's side, so the rule can be tested from either row. A failed write of the `ACC registration failed` record is an ordinary logging failure, so it uses AIR-040's allowance and the registration notice uses its own. This keeps OD-49 and OD-58 (`docs/spec/DECISIONS.md:57`, `:66`) unchanged and consistent with OD-101.

**AT rows.** All new offline checks use synthetic UI, audio and connection doubles and are specification evidence only (`specs/README.md`, Evidence rules). The `@unit` observation of the notice depends on a registration failure actually happening on the unit, so it is listed among the unexercised cases when that does not happen. AT-21 deliberately does not assert anything about a check-off notice until the owner decides.

## Reversibility and safety

- **Changes.** These rows install nothing and change nothing on this PC or the head unit. No file was edited in drafting.
- **Notice behaviour.** When implemented, the notice is UI only. It cannot unblock video, and it does not touch the gate, Park polling, registration, audio or the iPhone connection.
- **Logs.** Logging stays under the existing receiver log path set by AIR-039.
- **Undo.** At run time, restart the receiver: the next start resets both allowances, and a successful registration ends the blocked state under clause (h). In the specification, remove clause (i), AIR-040(c) and the added AT text.
- **Safety direction.** The safety direction is unchanged. With the check on, a registration failure still blocks video for the whole run; the notice only explains why.

## Open questions

1. **Check-off notice.** With the parking check off, should an ACC registration failure produce an on-screen notice? Nothing is blocked in that case, but Park polling stops for the run. Proposal: no notice, consistent with OD-45 showing nothing on screen with the check off; the failure is still logged. This is what the owner sees, so it is the owner's call.
2. **Wording, timing and duration.** What should the registration-failure notice say, for example whether it tells the user to restart the receiver from NEMESIS Manager (OD-95)? When should it appear, and for how long? Proposal: show it when the failure is detected, in the same form and for the same duration as AIR-040's notice, with text that says mirroring is off because the car's power state could not be read.
3. **Retry when the notice fails to show.** If the notice fails to show (for example, the UI is not yet ready), should it be tried again during that start? AIR-040's notice has the same gap. Proposal: no retry. The `ACC registration failed` record remains the evidence, and the gate is unaffected either way. This is what the owner sees, so it is listed rather than resolved.

AMB-71 (whether start should be held until the first ACC broadcast, `docs/spec/AMBIGUITY_REGISTER.md:81`) stays open and is not affected by this revision. New AMB numbers are left to the parent.
